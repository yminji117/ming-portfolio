**NEW CRITICAL — reopened by commit 5ce49c7 (2026-08-25), migration `supabase/migrations/0024_guestbook_remove_lockout.sql`:** `guestbook_verify(p_id, p_password)` was rewritten to drop ALL brute-force protection — no lockout, no fail counter, no rate limit of any kind, "순수 비밀번호 대조만" (pure password comparison only) per the migration's own comment. The `guestbook_auth_attempts` table and `guestbook_auth_status()` function are left in place but now completely unused (dead code, harmless). Since `guestbook_verify` is `security definer` + `grant execute to anon` and directly reachable via PostgREST with only the public anon key (same trust-boundary premise as the original 3 findings), and since it is also the sole gate inside `guestbook_apply_update` and `guestbook_apply_delete` (both call it internally before writing), an attacker can now call it as fast as the network allows with zero throttling. PRD 7.2 allows a 4-digit numeric password (10,000 combinations) — trivially exhaustible in well under a minute even single-threaded, faster with concurrency. Successful guess yields: (a) read of that entry's private `content` (never otherwise exposed — `guestbook_public` view excludes it), (b) ability to overwrite it via `guestbook_apply_update`, (c) ability to soft-delete it via `guestbook_apply_delete` (`0023_guestbook_delete.sql`, new in this same commit). No app-layer (`src/app/here/actions.ts`) or infra-layer rate limit compensates — `guestbook_insert`'s existing 60s/10-per-day limit (still intact, untouched by 0024) only throttles new posts, not `guestbook_verify` calls against existing entries. Confirmed via reading `0009_guestbook_functions.sql` (original, had 5-fail/10-min lockout keyed by guestbook_id+ip_hash) vs. `0024_guestbook_remove_lockout.sql`/`0025`/`0027`/`0028` (each `create or replace function guestbook_verify`, none reintroduce any throttling — final state as of 0028 has none). Fix: reintroduce a lockout/delay in `guestbook_verify` (the now-dead `guestbook_auth_attempts` table is sitting right there ready to be reused), or rate-limit by ip_hash+guestbook_id similar to `guestbook_insert`'s pattern.

**Verified correct in the same commit (5ce49c7):** the bcrypt prefix interop fix (`0027_guestbook_bcrypt_prefix_normalize.sql` + `0028_guestbook_bcrypt_prefix_fix2.sql`) is a real, mathematically sound fix, not cosmetic. Root cause: app hashes passwords with `bcryptjs` (produces `$2b$`-prefixed hashes) but pgcrypto's `crypt()` didn't recognize `$2b$`, so `v_hash = crypt(p_password, v_hash)` could never be true even for the correct password (registration worked, but verify/update/delete were permanently broken). Fix normalizes both the stored hash and the crypt() salt argument to `$2a$` via `regexp_replace(v_hash, '^\$2[abxy]\$', '$2a$')` before comparing. This is safe because `$2a$`/`$2b$`/`$2x$`/`$2y$` are byte-identical algorithms for passwords under ~255 bytes (the specific bug $2b$ fixed only affects passwords >255 bytes; the even-older $2a$-vs-$2x$/$2y$ split was an 8-bit-character handling bug, also irrelevant here) — and this app's guestbook password is capped at 16 chars (`PASSWORD_PATTERN` in `src/app/here/actions.ts`/`src/components/guestbook-form.tsx`), far under that threshold. Also confirmed Postgres `regexp_replace`'s replacement string uses `\1`-style backreferences (not `$1`), so the literal `'$2a$'` replacement string is not accidentally interpreted as a backreference — no injection/mangling risk. 0027 had a real bug (regex char class `[axy]` was missing `b`, so bcryptjs's actual `$2b$` output was never touched — silently a no-op fix); 0028 correctly adds `b` to the class. Also separately verified `0026_guestbook_variable_conflict_fix.sql`'s claimed bug is real (not just defensive): `guestbook_insert`'s rate-limit COUNT queries (`select count(*) ... where ip_hash = v_ip_hash and created_at > now() - interval '60 seconds'`) reference `created_at` *unqualified*, which collides with the `RETURNS TABLE(id, nickname, created_at)` output parameter of the same name — genuine "ambiguous column" error under plpgsql's default `variable_conflict` setting. `#variable_conflict use_column` correctly fixes it with no side effects (no bare `id`/`nickname`/`created_at` reference elsewhere in that function was relying on resolving to the local variable instead).

Migration sequencing note: 0023–0028 all use `create or replace function` (idempotent), and functions that call each other (e.g. `guestbook_apply_update`/`guestbook_apply_delete` calling `guestbook_verify`) resolve to the latest definition at call time since `CREATE OR REPLACE` preserves the function OID — so a fresh `0001`→`0028` apply lands in the correct final state with no broken intermediate window. All six files shipped in one commit (5ce49c7), so no partial-deploy risk in practice either.

**Update (2026-08-21, post-launch-commit recheck):** All 3 Critical findings below are confirmed fixed in the applied `0009_guestbook_functions.sql` + `src/app/here/actions.ts`: (1) `drop policy if exists "anyone can insert guestbook entry" on guestbook;` at line 12 removes the anon direct-INSERT bypass (the policy still exists in `0002_rls.sql` but migrations apply in numeric order, so 0009's drop wins — this is correct, not a leftover bug), (2) `guestbook_apply_update` now calls `guestbook_verify(p_id, p_password)` internally and raises `invalid_credentials` if not ok, (3) `guestbook_client_ip_hash()` derives IP server-side from the `request.headers` Postgres GUC rather than accepting a client-supplied `p_ip_hash` param; `src/app/here/actions.ts` no longer passes that param anywhere.

**New nuance found on recheck (not yet a confirmed bug, worth revisiting):** `guestbook_client_ip_hash()` (0009_guestbook_functions.sql:16-34) takes `split_part(x-forwarded-for, ',', 1)` — the *first* (leftmost) hop in the XFF chain. Standard XFF convention is that each proxy *appends* to the end of the list, so the leftmost value is whatever the original caller sent — which is attacker-controlled unless Supabase's own edge/gateway (Kong) is verified to strip or overwrite any client-supplied XFF before PostgREST sees it, rather than appending to it. If it appends, an attacker calling the RPC directly (bypassing the Next.js app, per this file's original trust-boundary premise) could set an arbitrary first XFF hop per request and cycle the derived IP hash, defeating the same rate-limit/lockout logic finding #3 was meant to fix. Could not verify Supabase's exact Kong XFF handling from the codebase alone — flag for the user to confirm directly (e.g. by testing what `request.headers ->> 'x-forwarded-for'` actually contains in a real request from an external caller), rather than assuming fixed.

Original findings (historical, kept for context):

Reviewed 2026-08-21, before `0009_guestbook_functions.sql` is applied to Supabase (user confirmed migration not yet run). Root cause across all three Critical findings: **the Next.js Server Action layer is not the real trust boundary — Supabase auto-exposes every function granted to `anon` via PostgREST using the public anon key, so any external caller can invoke these RPCs directly with fabricated parameters, bypassing the app entirely.**

1. **`supabase/migrations/0002_rls.sql:63-67`** (pre-existing policy, not touched by 0009) — `"anyone can insert guestbook entry" ... with check (true)` still grants anon direct `INSERT` on the raw `guestbook` table. This completely bypasses the rate-limiting (60s/10-per-day) and URL-spam-hold logic newly added in `guestbook_insert` (0009) — an attacker can `POST /rest/v1/guestbook` directly with no rate limit and no nickname/content format validation (no CHECK constraints exist on those columns either). Fix: `revoke insert on guestbook from anon;` (or drop the old policy) once `guestbook_insert` is the intended sole entry point, and add DB-level CHECK constraints on nickname/content length as defense in depth.

2. **`0009_guestbook_functions.sql:157-188` (`guestbook_apply_update`)** — never re-verifies a password or session token inside the DB function; it only checks the row exists. It's `security definer` + `grant execute to anon`, so anyone with the (public) anon key can call it directly via PostgREST with any guestbook `id` (ids are public via `guestbook_public` view) and rewrite that entry's content with zero authentication. The HMAC-signed cookie check in `src/app/here/actions.ts:154-156` (`verifyGuestbookSessionToken`) is application-layer only and provides no protection against direct RPC calls. Fix: require `p_password` again and re-verify via `crypt()` inside `guestbook_apply_update` itself (matching `guestbook_verify`'s pattern), or verify the HMAC token inside the DB function.

3. **`0009_guestbook_functions.sql:25-74` (`guestbook_insert`) and `:79-133` (`guestbook_verify`)** — both take `p_ip_hash` as a caller-supplied parameter rather than deriving it from a trusted source inside the function. Since these RPCs are directly reachable by anon over PostgREST, an attacker bypassing the Next.js app can pass a fresh random `p_ip_hash` on every call, which fully defeats (a) `guestbook_insert`'s 60s/daily rate limit and (b) `guestbook_verify`'s 5-fail/10-min lockout — making the 4-digit numeric password option (PRD 7.2, 10k combinations) trivially brute-forceable in seconds. `src/lib/request-ip.ts`'s XFF-trust question (asked by user) is moot until this is fixed, since the DB never sees a value it can trust regardless of how carefully the header is parsed app-side.

No SQL injection found anywhere — all four 0009 functions use plpgsql/sql with bound parameters (`$$ ... $$` + typed args), no dynamic `EXECUTE` with string concatenation. `src/lib/data.ts` and `src/lib/study.ts` slug lookups also use supabase-js `.eq()` query builder throughout (parameterized), no raw SQL string building anywhere in `src/`. `src/lib/guestbook-session.ts` HMAC design itself is solid (timingSafeEqual used correctly, length-checked before compare, expiry checked, throws loudly if `GUESTBOOK_SESSION_SECRET` is missing rather than silently degrading) — the flaw is that a valid-looking DB-layer authority never actually depends on that token at all.

Also re-confirmed the pre-Phase-2 finding in [[project_phase2_readiness_review]]: `CurrentlyDoing.ref_id`/`ref_type` still has no slug join anywhere (`currently-row.tsx`, `currently-doing-filterable-list.tsx`) — Phase 2 shipped `/works/[slug]` and `/study/[slug]` but never wired Currently Doing rows to link to them. Not a security bug, just an unresolved functional gap carried over.

**Why:** these are launch-blocking for `/here` guestbook once 0009 is applied — as designed, the guestbook's core anti-spam and anti-bruteforce guarantees described in PRD 7.4 do not actually hold against a direct API caller, only against someone using the Next.js UI honestly.

**How to apply:** before `0009_guestbook_functions.sql` is applied to Supabase, push back on merging until at least finding #1 (RLS insert bypass) and #3 (spoofable ip_hash) are fixed — #2 (apply_update auth) should also be fixed but is slightly lower blast radius (defacement of one's own or a known entry's text, not spam flood / brute force). Re-check `supabase/migrations/000*` for a new migration file that patches these before considering the guestbook security model closed.
